# Wallet Service — Database Migrations Guide

> **Why two migration files?**
> Migrations are split by concern. File `00001` builds the entire financial core — the tables that every wallet operation depends on. File `00002` adds the deposit/withdrawal lifecycle, which involves external payment bridges and is optional for the core trading loop to function. Splitting them means you can deploy the exchange and let users trade before the deposit/withdrawal feature is wired up.

---

## Migration 00001 — Core Wallet Tables

This file creates the **five foundational tables** that power every financial operation in TradeDrift.

---

### Table 1: `supported_assets`

**Purpose:** The single authoritative list of tradeable assets on the platform.

| Column | Type | Why it exists |
|---|---|---|
| `asset_code` | VARCHAR(10) PK | Short ticker symbol (e.g. `BTC`, `USDT`). Used as FK in every other table. |
| `asset_name` | VARCHAR(50) | Human-readable display name. |
| `decimals` | INT | Each asset has different precision. BTC = 8 decimals, USDT = 2. All balance math uses this. |
| `is_enabled` | BOOLEAN | Toggle an asset OFF without deleting it. Useful for pausing a market without data loss. |
| `seed_amount` | DECIMAL(30,10) | How much a new user starts with. USDT = 10,000 so users can immediately buy. Others = 0. |
| `display_order` | INT | Forces a fixed UI ordering (USDT first, then BTC, ETH, SOL). |

**Key design decision:** Adding a new tradeable asset (e.g. AVAX) is **a single INSERT into this table** — no code change, no redeploy. The `InitializeWallet` logic automatically picks it up and creates wallet rows for new users.

**Why separate from `wallets`?** Because `supported_assets` is platform config — it tells the system *what assets exist*. The `wallets` table tells the system *what a specific user owns*. Mixing them would duplicate asset metadata (name, decimals) in every wallet row.

---

### Table 2: `wallets`

**Purpose:** Holds the live balance state for each `(user, asset)` pair.

| Column | Type | Why it exists |
|---|---|---|
| `id` | UUID PK | Wallet identifier (UUIDv7, generated by the service). |
| `user_id` | UUID | The owner of this wallet. |
| `asset` | VARCHAR(10) FK | Which asset this wallet holds. References `supported_assets`. |
| `available_balance` | DECIMAL(30,10) | The balance a user can spend right now. Orders are only placed against this. |
| `reserved_balance` | DECIMAL(30,10) | Balance locked by an active order. Not spendable. |
| `is_frozen` | BOOLEAN | Admin can freeze a wallet (e.g. suspected fraud). Frozen wallets cannot transact. |
| `frozen_at/by/reason` | Various | Audit trail for why and when a wallet was frozen. |
| `initial_balance` | DECIMAL(30,10) | Snapshot of what the user started with. Used for PnL calculations. |
| `total_balance` | DECIMAL(30,10) | `available_balance + reserved_balance`. Total user holdings. |
| `UNIQUE(user_id, asset)` | Constraint | One wallet row per user per asset. Prevents duplicates. |
| `CHECK (available_balance >= 0)` | Constraint | DB-level invariant. Rejects any update that would make balance negative, even if code has a bug. |

**Why split `available_balance` and `reserved_balance`?**

When a user places a buy order for 100 USDT, that 100 USDT cannot be used for another order — but it hasn't left their account yet. So it moves:

```
available_balance -= 100   (money locked)
reserved_balance  += 100   (money held for this order)
```

After the trade fills, the reserved amount leaves the account. This two-bucket model prevents double-spending without distributed locks across services.

---

### Table 3: `wallet_reservations`

**Purpose:** Tracks exactly how much is locked per order, and how much has been consumed as fills arrive.

| Column | Type | Why it exists |
|---|---|---|
| `id` | UUID PK | Reservation identifier. |
| `order_id` | UUID UNIQUE | Links to a specific order. `UNIQUE` = one order, one reservation. |
| `reserved_amount` | DECIMAL | Full amount locked when the order was placed. **Never changes after creation.** |
| `consumed_amount` | DECIMAL | How much has been used by partial fills. Increases with each match. |
| `remaining_amount` | DECIMAL | `reserved_amount - consumed_amount`. What gets returned on cancellation. |
| `status` | VARCHAR | State machine tracking the reservation lifecycle. |

**Reservation state machine:**
```
ACTIVE
  ├── partial fill  → PARTIALLY_CONSUMED
  │       ├── more fills  → CONSUMED  (fully filled, nothing to return)
  │       └── cancelled   → RELEASED  (remaining_amount returned to available)
  └── cancelled     → RELEASED  (full reserved_amount returned)
```

**Why is this a separate table from `wallets`?**
A wallet tracks current balance (mutable, changes often). A reservation tracks the history of a specific order's fund lock (append-only, linked to order_id). Separate tables allow: *"How much is locked for order X?"* without scanning all wallet rows.

---

### Table 4: `wallet_transactions`

**Purpose:** Immutable ledger of every balance change. The financial audit trail and idempotency anchor.

| Column | Type | Why it exists |
|---|---|---|
| `id` | UUID PK | Transaction identifier. |
| `wallet_id` | UUID FK | Which wallet was affected. |
| `reference_id` | UUID | The ID of what caused this transaction (user_id, order_id, or trade_id). |
| `reference_type` | VARCHAR | What kind of operation caused this. See table below. |
| `transaction_type` | VARCHAR | `CREDIT` = money came in. `DEBIT` = money went out. |
| `asset` | VARCHAR | Which asset was moved. |
| `amount` | DECIMAL | How much moved. Always positive. |
| `UNIQUE(reference_id, reference_type, asset)` | Constraint | **The idempotency constraint** — see below. |

**`reference_type` mapping — what writes a transaction row:**

| `reference_type` | Triggered by gRPC method | `reference_id` | `transaction_type` |
|---|---|---|---|
| `INITIAL_ALLOCATION` | `InitializeWallet` | user_id | CREDIT |
| `RESERVATION` | `ReserveFunds` | order_id | DEBIT (available → reserved) |
| `RELEASE` | `ReleaseFunds` | order_id | CREDIT (reserved → available) |
| `SETTLEMENT` | `SettleTrade` | trade_id | CREDIT (2 rows: buyer + seller) |
| `DEPOSIT` | `DepositFunds` | external ref | CREDIT |
| `WITHDRAWAL` | `WithdrawFunds` | external ref | DEBIT |

**Why the `UNIQUE(reference_id, reference_type, asset)` constraint is critical:**

In distributed systems, network timeouts cause retries. Without this constraint:
1. Order Service calls `ReserveFunds` → times out
2. Order Service retries `ReserveFunds` → wallet service runs it again
3. User's balance is deducted **twice** — money manufactured from nothing

With this constraint:
1. First call → inserts transaction row ✅
2. Second call (retry) → `UNIQUE` violation detected → return success, no debit ✅

This is called **idempotency by database constraint**. A balance invariant is enforced at the lowest possible level.

**Accounting invariant:** `SUM(CREDIT) - SUM(DEBIT) = available_balance + reserved_balance` — always reconstructable from this table.

### Table 5: `outbox`

**Purpose:** Guarantees that Kafka events are published reliably after a database commit — the Transactional Outbox Pattern.

| Column | Type | Why it exists |
|---|---|---|
| `id` | UUID PK | Outbox event identifier. |
| `aggregate_id` | UUID | The entity that caused this event (e.g. trade_id, user_id). |
| `event_type` | VARCHAR | The Kafka event name (e.g. `wallet.trade_settled.v1`). |
| `payload` | JSONB | The full event body to publish to Kafka. |
| `partition_key` | VARCHAR | Which Kafka partition to use (typically `user_id` for per-user ordering). |
| `status` | VARCHAR | `PENDING` → publisher picks up → `PROCESSED`. Kafka down → `FAILED`. |
| `published_at` | TIMESTAMPTZ | When the event was successfully delivered to Kafka. |

**The problem the outbox solves:**

❌ **Without outbox** (naive approach):
```
1. Commit DB transaction (trade settled) ✅
2. Publish to Kafka ❌  ← Kafka is down for 2 minutes
3. Event lost — Portfolio Service never gets notified
```

✅ **With outbox:**
```
1. Write DB changes + insert outbox row → single atomic transaction ✅
2. Background publisher reads PENDING rows → publishes to Kafka → marks PROCESSED ✅
3. If Kafka was down, publisher retries automatically when it recovers — no events lost
```

The outbox row and the balance change live in the **same database transaction**. Either both happen or neither happens. This eliminates the "published but DB rolled back" and "DB committed but event lost" failure modes.

**Why the partial index?**
```sql
CREATE INDEX idx_outbox_pending ON outbox(created_at) WHERE status = 'PENDING';
```
This index only covers `PENDING` rows. As millions of rows become `PROCESSED`, they fall out of the index. The publisher's polling query (`WHERE status = 'PENDING'`) stays fast even years into production.

## Migration 00002 — Transfer Tables

This file adds the deposit/withdrawal lifecycle on top of the core tables.

---

### Table 6: `wallet_transfers`

**Purpose:** Tracks external money movements — real funds coming in (deposits) or going out (withdrawals).

| Column | Type | Why it exists |
|---|---|---|
| `id` | UUID PK | Transfer identifier. |
| `wallet_id` | UUID FK | Which wallet this transfer affects. |
| `type` | ENUM | `DEPOSIT` = money in. `WITHDRAWAL` = money out. |
| `amount` | DECIMAL | How much is being moved. |
| `status` | ENUM | `PENDING` = waiting for confirmation. `COMPLETED` = settled. `FAILED` = rolled back. |
| `reference_id` | VARCHAR UNIQUE | The external payment gateway's transaction ID. `UNIQUE` prevents the same deposit being credited twice. |

**Why is this separate from `wallet_transactions`?**

| Table | Answers the question |
|---|---|
| `wallet_transactions` | How did this user's internal balance change over time? |
| `wallet_transfers` | What external payments did this user make, and what's their current status? |

`wallet_transactions` is the internal ledger (every credit/debit). `wallet_transfers` is the external event log (bank wires, blockchain confirmations). One transfer can produce multiple transaction rows (e.g. a DEPOSIT produces a `wallet_transfers` row AND a `wallet_transactions` CREDIT row).

**Why use PostgreSQL ENUMs (`transfer_type`, `transfer_status`)?**
ENUMs are stored as integers internally — faster than VARCHAR comparisons. They enforce at the DB level that only valid values can be inserted. The tradeoff is that adding a new ENUM value requires an ALTER TYPE migration, which is why `wallet_transactions.reference_type` uses a VARCHAR CHECK instead — it can change more frequently.

## Why Two Files Instead of One?

| What it contains | File | Can deploy without the other? |
|---|---|---|
| Core trading: reserves, settlements, initialization, ledger, outbox | `00001` | ✅ Yes — the exchange can fully operate |
| External funding: deposits, withdrawals | `00002` | ✅ Yes — users trade with seeded USDT |

**Benefits of splitting:**
1. You can test the entire trading flow end-to-end with only `00001` applied.
2. Deposit/withdrawal can ship later as a separate feature — no risk to the core.
3. If `00002` has a bug, rolling back (`goose down`) only drops `wallet_transfers` — the trading core is untouched.
4. Clearer code reviews — a reviewer reading `00002` knows exactly what scope changed.

---

## Table Dependency Order

The tables must be created in this order because of foreign key dependencies:

```
supported_assets          ← no dependencies
     │
     └── wallets          ← FK → supported_assets.asset_code
              │
              ├── wallet_reservations   ← no FK to wallets, but logically depends on it
              ├── wallet_transactions   ← FK → wallets.id
              ├── outbox                ← no FK (standalone)
              └── wallet_transfers      ← FK → wallets.id  (migration 00002)
```

The `-- +goose Down` section drops tables in **reverse order** to satisfy these FK constraints.
