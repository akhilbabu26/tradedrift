# Wallet Service — Service Layer Guide

> **What is the service layer?**
> The service layer contains all business logic. It receives a request, decides *what* to do and *in what order*, and delegates database work to the repository layer. It knows the rules — the repositories just execute SQL.

## `service.go` — The Service Struct

```go
type Service struct {
    db               *pgxpool.Pool
    walletRepo       repository.WalletRepository
    reservRepo       repository.ReservationRepository
    txnRepo          repository.TransactionRepository
    assetRepo        repository.AssetRepository
    outboxRepo       repository.OutboxRepository
    settledTradeRepo repository.SettledTradeRepository
    log              *zap.Logger
}
```

The service holds **interfaces**, not concrete types. This means:
- Unit tests can inject mock repositories — no real database needed
- The postgres implementation can be swapped for a different database without touching business logic

`NewService(db, log)` is the only constructor — it wires all 6 postgres implementations internally.

## `initialize_wallet.go` — `InitializeWallet`

```go
func (s *Service) InitializeWallet(ctx context.Context, userID string) error
```

**Purpose:** Create one wallet row per supported asset for a new user and seed USDT with a starting balance.

**Idempotent:** Calling it twice for the same user never duplicates wallets or credits.

### Steps:
1. `assetRepo.GetEnabled()` — fetch the live list of enabled assets
2. For each asset, `walletRepo.GetByUserAndAsset()` — skip if wallet already exists
3. Generate UUIDv7 wallet ID
4. `walletRepo.Create()` — insert wallet row with seed balance
5. If `seed_amount > 0` (only USDT): generate UUIDv7 txn ID → `txnRepo.Create()` — write `INITIAL_ALLOCATION CREDIT` ledger entry
6. Log success

**Why dynamic asset list?** Adding a new asset (AVAX) requires only an `INSERT` into `supported_assets` — no code change.

**Why UUID generated by service, not DB?** The service needs the ID before insertion to pass it to the ledger row. No extra DB round-trip.

## `reserve_funds.go` — `ReserveFunds`

```go
func (s *Service) ReserveFunds(ctx context.Context, userID, orderID, asset, amount string) (*repository.Reservation, error)
```

**Purpose:** Lock funds for an order. Moves `amount` from `available_balance → reserved_balance`.

**Idempotent:** If a reservation already exists for `orderID`, returns the existing one immediately.

### Steps:
1. `reservRepo.GetByOrderID()` — already reserved? Return existing (idempotent replay)
2. `walletRepo.GetByUserAndAsset()` — does wallet exist?
3. Check `wallet.IsFrozen` — return `ErrWalletFrozen` if true
4. `txnRepo.ExistsByKey()` — upfront idempotency check (before touching balances)
5. `walletRepo.MoveToReserved()` — atomic: `available -= amount`, `reserved += amount`
   - SQL uses `WHERE available_balance >= amount` — fails safely if insufficient funds
6. `reservRepo.Create()` — insert reservation row (ACTIVE status)
7. `txnRepo.Create()` — write `RESERVATION DEBIT` ledger entry
8. Log and return reservation

**Key guarantee:** The `WHERE available_balance >= amount` in the SQL makes the fund lock atomic. Two concurrent orders for the same user cannot both succeed if only one has sufficient balance — no distributed lock needed.

## `release_funds.go` — `ReleaseFunds`

```go
func (s *Service) ReleaseFunds(ctx context.Context, orderID string) error
```

**Purpose:** Return reserved funds to available balance when an order is cancelled.

**Idempotent:** If reservation is already RELEASED or CONSUMED, returns success immediately.

### Steps:
1. `reservRepo.GetByOrderID()` — fetch the reservation
2. Check `status == RELEASED || CONSUMED` — already done, skip
3. `walletRepo.GetByUserAndAsset()` — fetch the wallet
4. `txnRepo.ExistsByKey()` — check ledger for existing RELEASE entry (repair case)
5. If ledger entry exists but status isn't RELEASED → fix status only (consistency repair)
6. `walletRepo.MoveFromReserved()` — move `remaining_amount` back to available
7. `reservRepo.UpdateStatus(RELEASED)` — mark reservation done
8. `txnRepo.Create()` — write `RELEASE CREDIT` ledger entry
9. Log and return

**`remaining_amount` not `reserved_amount`:**
An order may have been partially filled before cancellation. `remaining_amount = reserved_amount - consumed_amount`. Only the unconsumed portion is returned.

## `settle_trade.go` — `SettleTrade`

```go
func (s *Service) SettleTrade(ctx context.Context, req TradeSettlementRequest) error
```

**Purpose:** After a trade match, execute atomic multi-asset two-sided balance movement (both BaseAsset and QuoteAsset) between buyer and seller, write double-entry ledger records, and emit 3 outbox events.

**Idempotent:** Primary idempotency barrier is `INSERT INTO settled_trades ... ON CONFLICT (trade_id) DO NOTHING` (Migration 00005). Backed up by DB unique constraint `UNIQUE (wallet_id, reference_id, reference_type)` on `wallet_transactions` (Migration 00004). Duplicate calls return success immediately without double debits.

### 1-Atomic Transaction Steps:
1. **Validation:** Rejects self-trades, identical buy/sell order IDs, non-positive amounts, or missing IDs (`ErrInvalidSettlement`).
2. **Begin Transaction:** `tx, err := s.db.Begin(ctx)` with `defer tx.Rollback(ctx)`. Repositories are transaction-scoped via `WithTx(tx)`.
3. **Primary Idempotency Registration:** `settledTradeRepo.RegisterSettlement(tradeID, marketID, sequence)`. If row already exists (`!inserted`), logs debug and returns `nil`.
4. **Deterministic Reservation Locking:** Sorts `BuyOrderID` and `SellerOrderID` alphabetically before fetching via `reservRepo.GetByOrderIDForUpdate()` (`SELECT ... FOR UPDATE`). Completely prevents deadlocks between concurrent crossed trades.
5. **Domain Validation:** Asserts both reservations exist, are not released, match their corresponding assets (seller=BaseAsset, buyer=QuoteAsset), and belong to their respective users.
6. **Leg 1 (Base Asset Transfer: Seller → Buyer):**
   - Debits seller's `reserved_balance` for `BaseAsset`.
   - `reservRepo.ConsumeRemaining()` atomically decrements seller reservation remaining amount in SQL.
   - Credits buyer's `available_balance` for `BaseAsset`.
7. **Leg 2 (Quote Asset Transfer: Buyer → Seller):**
   - Debits buyer's `reserved_balance` for `QuoteAsset`.
   - `reservRepo.ConsumeRemaining()` atomically decrements buyer reservation remaining amount in SQL.
   - Credits seller's `available_balance` for `QuoteAsset`.
8. **Write Ledger Entries:** `txnRepo.CreateBatch()` writes 4 records:
   - Seller Base DEBIT
   - Buyer Base CREDIT
   - Buyer Quote DEBIT
   - Seller Quote CREDIT
   If DB unique constraint violation occurs, it is handled gracefully as idempotent replay.
9. **Write 3 Outbox Events:**
    - `TradeSettled` (partition key: `BuyerUserID`, topic: `trades.settled.v1`) $\rightarrow$ consumed by Trade Service
    - `PortfolioUserTrade` BUY leg (partition key: `BuyerUserID`, role: `BUY`, topic: `portfolio.user.trades.v1`) $\rightarrow$ consumed by Portfolio Service
    - `PortfolioUserTrade` SELL leg (partition key: `SellerUserID`, role: `SELL`, topic: `portfolio.user.trades.v1`) $\rightarrow$ consumed by Portfolio Service
10. **Commit Transaction:** `tx.Commit(ctx)`. If any step fails, all balance debits/credits, reservation consumptions, ledger records, `settled_trades` row, and outbox events roll back completely.

## `get_balance.go` — `GetBalance` + `GetBalances`

```go
func (s *Service) GetBalance(ctx context.Context, userID, asset string) (*repository.Wallet, error)
func (s *Service) GetBalances(ctx context.Context, userID string) ([]*repository.Wallet, error)
```

**Purpose:** Read-only balance queries for the API Gateway.

- `GetBalance` — single `(user, asset)` lookup. Used for asset-specific balance display.
- `GetBalances` — all wallets for a user, ordered by `display_order` (USDT first). Used for the full dashboard view.

No idempotency needed — these are pure reads, no state change.

## `get_assets.go` — `GetSupportedAssets`

```go
func (s *Service) GetSupportedAssets(ctx context.Context) ([]*repository.SupportedAsset, error)
```

**Purpose:** Returns all enabled assets on the platform.

Used by the **Market Service** to validate that base/quote asset codes are valid before creating a trading pair. Returns only `is_enabled = true` assets — disabled assets are invisible to trading operations.

## Common Patterns Across All Methods

### Idempotency at Two Levels

Every state-changing method guards against duplicate calls at **two levels**:

| Level | Mechanism | What it catches |
|---|---|---|
| Application | Check reservation status or `ExistsByKey` before touching balances | The normal retry case |
| Database | `UNIQUE(wallet_id, reference_id, reference_type)` on `wallet_transactions` (Migration 00004) | Race condition — two concurrent calls both passed the app check |


### Typed Constants

All status strings and reference types use constants from `repository/constants.go`:

```go
// ✅ compile-time checked
reservation.Status == repository.ReservationReleased
txn.ReferenceType  = repository.RefSettlement

// ❌ magic string — typo compiles silently
reservation.Status == "RELASED"
```

### Error Wrapping

All errors are wrapped with `fmt.Errorf("context: %w", err)`. This preserves the original error in the chain so the handler can use `errors.Is()` to check for sentinel errors:

```go
// In service:
return fmt.Errorf("failed to fetch wallet: %w", repository.ErrNotFound)

// In handler:
errors.Is(err, repository.ErrNotFound)  // → true ✅
```

### Structured Logging

Every method logs success at `Info` level and idempotent skips at `Debug` level. Debug lines are invisible in production (log level `info`) but visible during development.

## Idempotency Summary

| Method | Key | Guard |
|---|---|---|
| `InitializeWallet` | `(user_id, asset_code)` | Check existing wallet before create |
| `ReserveFunds` | `order_id` | Return existing reservation if found |
| `ReleaseFunds` | reservation `status` | Skip if `RELEASED` or `CONSUMED` |
| `SettleTrade` | `trade_id` | Primary: `RegisterSettlement` on `settled_trades`; Secondary: `UNIQUE(wallet_id, reference_id, reference_type)` on `wallet_transactions` |
