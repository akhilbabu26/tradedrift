# Notification Service — Database Migrations Guide

This document provides an in-depth technical explanation of all database migrations for the **TradeDrift Notification Service** located in `services/notification/migration/`.

It details the architectural purpose of each migration file, the specific distributed-systems and data-integrity problems each file solves, the design of tables, columns, indexes, and constraints, and how data flows through these structures at runtime.

---

## Migration Architecture Overview

The Notification Service uses [Goose](https://github.com/pressly/goose) for schema versioning. Migrations are written in plain SQL with standard `-- +goose Up` and `-- +goose Down` annotations.

```
services/notification/migration/
├── 00001_create_notifications.sql                  # Persistent user inboxes & deduplication log
├── 00002_create_notification_outbox.sql              # Transactional outbox table & partial polling index
└── 00003_add_notification_id_and_claim_token.sql     # Lease ownership, idempotency recovery & check constraints
```

### Lifecycle & Execution Order
1. **Bootstrapping**: On application startup, `cmd/server/main.go` executes `platformpg.RunMigrations(cfg.PostgresDSN, cfg.MigrationsDir)`.
2. **Deterministic Locking**: Goose tracks migration versions in the `goose_db_version` table, acquiring an advisory lock to prevent multiple service replicas from applying migrations concurrently.
3. **Fail-Fast Boundary**: If any migration fails, the service immediately halts with `appLogger.Fatal()`, preventing the microservice from starting with an out-of-sync schema.

## 1. `00001_create_notifications.sql` — Inboxes & Deduplication

### Purpose
Establishes the primary durable storage for user notifications and the atomic deduplication boundary for incoming Kafka domain events.

### Problems It Solves
1. **Unreliable Delivery / Missing Inboxes**: User alerts (trade executions, order cancellations, account security notices) must be permanently retained for query via REST and WebSocket, even if the user is offline.
2. **Duplicate Kafka Processing**: Distributed message brokers like Kafka guarantee **at-least-once** delivery. Network retries, partition rebalances, or consumer restarts will redeliver the same domain event (`trades.settled.v1`). Without an idempotent deduplication boundary, a user would receive duplicate notifications and trade alerts.

---

### Schema Breakdown & Field Explanations

#### Table: `notifications`
Stores durable notifications for user inboxes.

```sql
CREATE TABLE IF NOT EXISTS notifications (
    id             UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    user_id        UUID NOT NULL,
    title          VARCHAR(255) NOT NULL,
    message        TEXT NOT NULL,
    type           VARCHAR(30) NOT NULL,
    reference_id   UUID,
    reference_type VARCHAR(30),
    is_read        BOOLEAN NOT NULL DEFAULT FALSE,
    read_at        TIMESTAMPTZ,
    created_at     TIMESTAMPTZ NOT NULL DEFAULT NOW()
);
```

| Column | Type | Description & Purpose |
|---|---|---|
| `id` | `UUID PRIMARY KEY` | Unique notification identifier (UUIDv7 generated by Go service; fallback `gen_random_uuid()`). Used as a stable cursor tiebreaker during keyset pagination. |
| `user_id` | `UUID NOT NULL` | Ownership boundary. All queries enforce `WHERE user_id = $1` to isolate user inboxes and prevent cross-tenant data leakage. |
| `title` | `VARCHAR(255) NOT NULL` | Short alert headline displayed in web/mobile UI cards (e.g. `"Trade Executed"`). |
| `message` | `TEXT NOT NULL` | Formatted, privacy-sanitized notification body. Contains no counterparty secrets. |
| `type` | `VARCHAR(30) NOT NULL` | Category classifier: `'INFO'`, `'TRADE_FILL'`, `'SYSTEM'`, `'ACCOUNT'`. Used by UI for filtering and badge counts. |
| `reference_id` | `UUID` | Optional foreign UUID pointing to the underlying entity (`trade_id`, `order_id`, or `deposit_id`). |
| `reference_type` | `VARCHAR(30)` | Domain discriminator for `reference_id`: `'TRADE'`, `'ORDER'`, `'DEPOSIT'`. |
| `is_read` | `BOOLEAN NOT NULL` | Read/unread badge state. Defaults to `FALSE`. |
| `read_at` | `TIMESTAMPTZ` | Timestamp when the user marked the notification as read. Set to `NULL` while unread. |
| `created_at` | `TIMESTAMPTZ NOT NULL` | Record creation timestamp. Primary sorting key for inbox timelines. |

---

#### Index: `idx_notifications_user_inbox`
```sql
CREATE INDEX IF NOT EXISTS idx_notifications_user_inbox 
    ON notifications(user_id, created_at DESC, id DESC);
```

#### Problem Solved by this Index:
Standard `OFFSET / LIMIT` pagination suffers from:
1. **O(N) Degradation**: High offsets require scanning thousands of dead tuples.
2. **Page Drift**: If a new notification arrives while a user scrolls from Page 1 to Page 2, records shift and users see duplicate items.

#### How It Solves It:
- Forms a **composite B-Tree** matching the exact keyset pagination query:
  ```sql
  WHERE user_id = $1 
    AND (created_at, id) < ($2, $3)
  ORDER BY created_at DESC, id DESC 
  LIMIT $4
  ```
- Including `id DESC` provides a deterministic tiebreaker if two notifications share the exact same microsecond timestamp.
- The PostgreSQL query planner performs a direct index seek and index-only range scan with $O(\log N)$ efficiency.

---

#### Table: `processed_events`
The deduplication registry for distributed event ingestion.

```sql
CREATE TABLE IF NOT EXISTS processed_events (
    event_id      UUID PRIMARY KEY,
    user_id       UUID,
    processed_at  TIMESTAMPTZ NOT NULL DEFAULT NOW()
);
```

| Column | Type | Description & Purpose |
|---|---|---|
| `event_id` | `UUID PRIMARY KEY` | The source domain event UUID from Kafka (`ev.EventID`) or caller idempotency key. |
| `user_id` | `UUID` | Associated user identity (nullable for multi-user events like dual trade fills). |
| `processed_at`| `TIMESTAMPTZ NOT NULL` | Audit timestamp recording when the event was first committed. |

#### Problem Solved:
When Kafka delivers an event:
```sql
INSERT INTO processed_events (event_id, user_id) 
VALUES ($1, $2)
```
- If the `event_id` already exists, PostgreSQL raises a **Primary Key Unique Violation (SQLSTATE 23505)**.
- The repository catches this error and returns `repository.ErrAlreadyProcessed`.
- The consumer safely skips message processing and immediately commits the Kafka offset without writing duplicate inbox rows.

## 2. `00002_create_notification_outbox.sql` — Transactional Outbox

### Purpose
Creates the durable staging table for real-time WebSocket publishing via Redis Pub/Sub, implementing the **Transactional Outbox Pattern**.

### Problems It Solves
1. **The Dual-Write Dilemma**: In microservices, updating a database and publishing to a message broker (Redis) cannot be done atomically without 2-Phase Commit (2PC). If the database commit succeeds but Redis fails, the real-time alert is permanently lost. If Redis publish happens first and the database transaction rolls back, users receive phantom alerts for trades that never persisted.
2. **Outage Data Loss**: If Redis crashes or undergoes maintenance, outbox events accumulate durably in PostgreSQL. Once Redis recovers, background publishers resume without losing a single message.

---

### Schema Breakdown & Field Explanations

#### Table: `notification_outbox`
```sql
CREATE TABLE IF NOT EXISTS notification_outbox (
    id             UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    event_type     VARCHAR(50) NOT NULL,
    payload        JSONB NOT NULL,
    target_channel VARCHAR(100) NOT NULL,
    status         VARCHAR(20) NOT NULL DEFAULT 'PENDING',
    retry_count    INT NOT NULL DEFAULT 0,
    last_error     TEXT,
    claimed_at     TIMESTAMPTZ,
    created_at     TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    published_at   TIMESTAMPTZ
);
```

| Column | Type | Description & Purpose |
|---|---|---|
| `id` | `UUID PRIMARY KEY` | Unique identifier of the outbox entry. |
| `event_type` | `VARCHAR(50) NOT NULL` | Event classifier (e.g. `'NotificationCreated'`, `'PortfolioUpdated'`). |
| `payload` | `JSONB NOT NULL` | The full Redis envelope (`model.RedisEnvelope`) containing `event_id`, `notification_id`, timestamp, and payload. |
| `target_channel` | `VARCHAR(100) NOT NULL`| Exact Redis Pub/Sub channel destination (e.g. `user:notifications:{uuid}` or `user:portfolio:{uuid}`). |
| `status` | `VARCHAR(20) NOT NULL` | Lifecycle state: `'PENDING'`, `'PROCESSING'`, `'PROCESSED'`, `'FAILED'`. |
| `retry_count` | `INT NOT NULL DEFAULT 0` | Counter tracking how many times publication to Redis was attempted. |
| `last_error` | `TEXT` | Diagnostic error string captured from the most recent Redis failure. |
| `claimed_at` | `TIMESTAMPTZ` | Timestamp when a publisher worker claimed this event for publishing. |
| `created_at` | `TIMESTAMPTZ NOT NULL` | When the outbox event was staged. |
| `published_at` | `TIMESTAMPTZ` | Timestamp when Redis confirmed delivery and the event was marked `PROCESSED`. |

---

#### Index: `idx_notification_outbox_pending`
```sql
CREATE INDEX IF NOT EXISTS idx_notification_outbox_pending 
    ON notification_outbox(created_at) 
    WHERE status IN ('PENDING', 'PROCESSING');
```

#### Problem Solved by this Index:
Over weeks of trading, the outbox table accumulates millions of `PROCESSED` rows. A normal index on `created_at` would index every single historical row, requiring massive disk I/O and slowing down the publisher loop.

#### How It Solves It:
- **Partial Index**: Only indexes rows where `status IN ('PENDING', 'PROCESSING')`.
- Once a row transitions to `PROCESSED`, PostgreSQL automatically removes it from this index.
- The index remains tiny (fits entirely in RAM), allowing the publisher's `SELECT ... FOR UPDATE SKIP LOCKED` query to execute in under 1 millisecond regardless of table size.

## 3. `00003_add_notification_id_and_claim_token.sql` — Hardening & Idempotency

### Purpose
Harden the transactional outbox against concurrent worker races, enable retry idempotency for gRPC calls, and enforce closed-enum data integrity constraints.

### Problems It Solves
1. **Outbox Lease Expiry Race**: If Worker A claims an outbox record and experiences a 65-second network stall, its 60-second lease expires. Worker B re-claims the event. When Worker A recovers, it must **not** be allowed to mark the row `PROCESSED` or reset it to `PENDING`, which would interfere with Worker B's execution.
2. **gRPC Retry Duplication**: When internal microservices (Wallet, Auth) invoke `CreateNotification`, a dropped network packet or client timeout can cause the client to retry. Without tracking the created `notification_id`, the retry would either fail with a duplicate error or create a second notification.
3. **Database Invariant Drift**: Prevents invalid statuses (`status = 'UNKNOWN'`) or invalid notification types from corrupting database rows.

---

### Statements Breakdown

#### 1. Claim Ownership Tracking (`claim_token`)
```sql
ALTER TABLE notification_outbox
    ADD COLUMN IF NOT EXISTS claim_token UUID;
```
- When `FetchPendingOutbox` claims a batch of rows, it generates a fresh UUID (`claimToken`) and stores it in `claim_token`.
- `MarkOutboxPublished`, `ReleaseOutboxClaims`, and `IncrementOutboxRetry` require `AND claim_token = $claimToken`.
- If another worker re-claimed the row after a lease expiry, the token will not match. The query affects 0 rows, returning `repository.ErrOutboxClaimLost`, which is logged safely without corrupting worker state.

#### 2. Idempotent Retry Lookup (`notification_id`)
```sql
ALTER TABLE processed_events
    ADD COLUMN IF NOT EXISTS notification_id UUID;
```
- Extends the deduplication registry to store the created `notification_id` alongside the caller's `idempotency_key`.
- On retry, if `CreateWithDedupTx` returns `ErrAlreadyProcessed`, the service queries `GetNotificationIDByEventID(ctx, idempotencyKey)` and returns the existing notification to the caller. Zero duplicate notifications are created.

#### 3. Closed-Enum Check Constraints
```sql
ALTER TABLE notification_outbox
    ADD CONSTRAINT chk_outbox_status
    CHECK (status IN ('PENDING', 'PROCESSING', 'PROCESSED', 'FAILED'));

ALTER TABLE notifications
    ADD CONSTRAINT chk_notification_type
    CHECK (type IN ('INFO', 'TRADE_FILL', 'SYSTEM', 'ACCOUNT'));

ALTER TABLE notifications
    ADD CONSTRAINT chk_notification_reference_type
    CHECK (reference_type IS NULL OR reference_type IN ('TRADE', 'ORDER', 'DEPOSIT'));
```
- Enforces data integrity at the database layer. Any SQL insert or update containing an unsupported status, notification type, or reference type is immediately rejected by PostgreSQL with a constraint violation.

## Complete Runtime Data Flows

### Flow A: Ingestion & Transactional Outbox Stage
```
Incoming Event (Kafka TradeSettled / OrderCancelled)
   │
   ▼
service.HandleTradeSettled()
   │
   ▼
repository.CreateTradeSettledTx() ─── PostgreSQL Transaction
   │
   ├── 1. INSERT INTO processed_events (event_id, notification_id)
   │      └── Raises Unique Violation if already processed (Dedup Guard)
   │
   ├── 2. INSERT INTO notifications (buyer_notif)
   ├── 3. INSERT INTO notifications (seller_notif)
   │      └── Indexed by idx_notifications_user_inbox
   │
   ├── 4. INSERT INTO notification_outbox (buyer_outbox, status='PENDING')
   └── 5. INSERT INTO notification_outbox (seller_outbox, status='PENDING')
          └── Added to partial index idx_notification_outbox_pending
```

---

### Flow B: Outbox Polling & Claim-Token Ownership
```
publisher.ProcessBatch()
   │
   ▼
SELECT id FROM notification_outbox
WHERE status = 'PENDING' OR (status = 'PROCESSING' AND claimed_at < NOW() - 60s)
ORDER BY created_at ASC
LIMIT 50
FOR UPDATE SKIP LOCKED; ─── (Uses partial index idx_notification_outbox_pending)
   │
   ▼
UPDATE notification_outbox
SET status = 'PROCESSING',
    claimed_at = NOW(),
    claim_token = '018f-claim-token-uuid'
WHERE id = ANY(claimed_ids)
RETURNING *;
   │
   ▼
Publish to Redis (user:notifications:{user_id})
   │
   ├── On Success:
   │      UPDATE notification_outbox
   │      SET status = 'PROCESSED', published_at = NOW(), claim_token = NULL
   │      WHERE id = $id AND status = 'PROCESSING' AND claim_token = $claimToken;
   │      (Removed from partial index idx_notification_outbox_pending)
   │
   └── On Failure:
          UPDATE notification_outbox
          SET retry_count = retry_count + 1, last_error = $err
          WHERE id = $id AND status = 'PROCESSING' AND claim_token = $claimToken;
```

---

### Flow C: gRPC `CreateNotification` Retry Idempotency
```
Caller sends CreateNotification(idempotency_key = "018f-key-uuid")
   │
   ├── Attempt 1:
   │      INSERT INTO processed_events (event_id, notification_id)
   │      VALUES ("018f-key-uuid", "018f-notif-uuid");
   │      INSERT INTO notifications (id = "018f-notif-uuid", ...);
   │      Returns "018f-notif-uuid" to caller.
   │
   └── Attempt 2 (Network dropped response, caller retries with exact same key):
          INSERT INTO processed_events fails (PRIMARY KEY Unique Constraint).
          Service detects ErrAlreadyProcessed.
          Queries: SELECT notification_id FROM processed_events WHERE event_id = "018f-key-uuid";
          Queries: SELECT * FROM notifications WHERE id = notification_id;
          Returns original notification object. (No duplicates created).
```
